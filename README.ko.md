## 왜 NULNUL인가요?

AI 코딩 에이전트 자체는 강력하지만, 그 주변의 프로젝트별 설정은 쉽게 복잡해집니다. 규칙은 중복되고, 스킬은 계속 쌓이고, 컨텍스트는 낡아 갑니다. 실제 테스트를 통과했는지 확인하지 않고 모델의 판단만으로 작업을 완료 처리하기도 합니다.

NULNUL은 이러한 설정을 **프로젝트의 요구와 검증 근거**에 따라 관리합니다.

| NULNUL 없이 | NULNUL과 함께 |
| --- | --- |
| 세션마다 프로젝트를 다시 설명 | 검증된 프로젝트 상태에서 이어서 작업 |
| 익숙한 규칙과 스킬을 한꺼번에 불러옴 | 현재 작업에 필요한 기능만 선택 |
| 완료 메시지를 믿음 | 저장소의 실제 테스트·빌드·검증 명령 실행 |
| AI 설정을 계속 추가 | 근거가 있을 때만 유지·개선·교체·병합·사용 중단·생성 |
| 채팅에서 과거 작업을 복원 | 검증된 작업 기록(Experience) 중 관련 항목만 재사용 |

현재 프로젝트 설정이 근거상 가장 적합하다면 **아무것도 추가하지 않는 것이 올바른 결과**입니다.

## 빠른 시작

결과물부터 보고 싶다면 **[NULNUL in Action](examples/README.ko.md)**을 확인하세요. 로컬 예약 화면·API 데모, 합성 조사 데이터 워크북 예제, 기존 프로젝트의 3.1.0 도입 기록을 모았습니다. 사례마다 증거와 한계를 구분하며, 독립적으로 검증한 고객 프로젝트 3개나 새로운 성능 벤치마크를 의미하지 않습니다.

공개 `v3.2.0`은 새롭게 수행한 Claude·Meta 도입 검증을 통과했습니다. 아래 명령으로 설치할 수 있습니다. 플러그인 명령을 지원하는 Codex 또는 Claude Code를 사용하고 호스트의 신뢰·권한 확인 절차를 따르세요. 특정 버전으로 고정해 설치하면 이후 릴리스로 자동 업데이트되지 않습니다.

### OpenAI Codex

```bash
codex plugin marketplace add SeoNaRu/nulnul-harness --ref v3.2.0
codex plugin add nulnul-harness@nulnul-harness
```

### Anthropic Claude Code

```bash
claude plugin marketplace add 'https://github.com/SeoNaRu/nulnul-harness.git#v3.2.0'
claude plugin install nulnul-harness@nulnul-harness
```

처음 도입할 때는 기존 하네스가 있는 저장소에서도 다음처럼 요청하세요.

```text
기존 프로젝트 지침과 에이전트 역할을 보존하면서 이 저장소에 NULNUL을 설정해줘.
이어서 예약 API를 수정하고 기존 동작에 문제가 없는지 검증해줘.
```

이미 NULNUL을 사용하는 프로젝트에서는 필요한 작업만 말하면 됩니다.

```text
예약 API를 수정하고 기존 동작에 문제가 없는지 검증해줘.
```

이것이 NULNUL의 기본 사용 방식입니다. 사용자가 직접 스킬을 고르거나, 세션을 만들거나, 기억(Memory)을 저장하거나, 에이전트 수를 정하거나, 진화 절차(Evolution)를 실행할 필요는 없습니다.

로컬 작업 계약에 필요한 지침이 모두 갖춰져 있다면 Direct 경로로 바로 처리할 수 있습니다. 플러그인을 설치했다고 모든 요청에 설정 작업이나 영구 기억을 강제하지 않습니다.

이전 공개 버전으로 고정해 설치했다면, 사용하는 호스트에 맞게 `codex plugin marketplace remove nulnul-harness` 또는 `claude plugin marketplace remove nulnul-harness --scope user`로 이전 참조를 제거한 뒤 위 설치 명령을 다시 실행하세요. 새 세션에서 프로젝트 지침과 역할을 보존하며 기존 NULNUL 설정을 업그레이드하도록 요청하세요. 패키지 갱신이 기존 프로젝트 진입 파일까지 자동으로 바꾸지는 않습니다.

기존 NULNUL 프로젝트에는 [3.0 기반 구조 업그레이드 안내](docs/upgrade-3.0.md)가 계속 적용되며, 3.2에서도 기존 체크포인트 형식은 바뀌지 않습니다. 직접 관리하는 Setup Plan이 있다면 확인한 기존 역할을 이름만 적지 말고 `이름: 분류`로 기록해야 합니다. 허용 값은 `reuse`, `kept`, `upgraded`, `merged`, `removed`이며, `kept`는 `reuse`로 정규화됩니다.

## NULNUL이 하는 일

### 1. 채팅이 아니라 프로젝트를 이어갑니다

NULNUL은 세션(Session), 작업 인계, 작업 기록(Experience), 결정(Decision), 교훈(Lesson), 미해결 작업(Open Thread)을 필요한 범위만큼 유지합니다. 다음 세션에서는 대화를 처음부터 재생하지 않고 **현재 작업과 관련된 검증된 기억만** 복원합니다.

작업이 중간에 끊기면 완료했다고 처리하지 않고, 복구해 이어갈 수 있는 상태로 남깁니다.

### 2. 작업에 맞는 Capability Pack을 만듭니다

작업을 시작하기 전에 결과 품질과 검증 가능성을 고려해, 근거상 가장 적합한 기능을 고릅니다. 결과가 실질적으로 동등한 경로 사이에서만 컨텍스트·조정·실행·유지보수·권한 비용이 더 낮은 구성을 선택합니다. 기능이나 에이전트 수 자체가 우선 목표는 아닙니다.

```text
작업
 ↓
프로젝트 + 관련 Memory
 ↓
Capability 선택
 ↓
Pre-Session Capability Pack
 ↓
작업 실행
```

명확한 Direct 작업에는 **기능(Capability)의 상세 지침을 불러오지 않습니다.** 필요한 작업에만 선택한 기능의 상세 지침이 들어갑니다.

### 3. 실제 프로젝트 검사로 결과를 확인합니다

NULNUL은 모델의 자신감을 완료 근거로 사용하지 않습니다.

```text
작업
 ↓
저장소 test / build / validation
 ↓
Authoritative Check receipt
 ↓
Verified Experience
```

중요한 것은 에이전트의 “잘된 것 같습니다”가 아니라 프로젝트의 실제 검사 결과입니다.

### 4. 검증된 작업 기록을 기억합니다

검증된 작업 결과는 출처 정보와 함께 Experience로 남습니다. 다음 세션에서는 관련 기록만 재사용하며, 대화 원문 전체를 일반적인 기억이나 컨텍스트에 넣지 않습니다.

### 5. 근거가 있을 때만 진화합니다

NULNUL은 계속 자기 자신을 뜯어고치지 않습니다.

기능의 유지·변경 여부는 다음과 같이 판단합니다.

```text
KEEP · UPGRADE · REPLACE · MERGE · RETIRE · CREATE
```

`KEEP`(유지)도 정상적인 진화 결과입니다. 검증된 약점이 없다면 현재 기능을 그대로 유지합니다.

외부 기능 비교, 에이전트 구성 변경, 하네스 제어 방식 변경, 다른 프로젝트의 사전 지식 재사용도 모두 **근거가 생겼을 때만** 평가합니다.

## NULNUL 한눈에 보기

```text
사용자 작업
   ↓
SESSION + PROJECT CONTEXT
   ↓
관련 MEMORY
   ↓
에이전트 구성 검토
   ↓
CAPABILITY PACK
   ↓
작업
   ↓
프로젝트가 정한 검증
   ↓
EXPERIENCE
   ↓
MEMORY
   ↓
증거가 있을 때만 EVOLUTION
   ├─ Capability Natural Selection
   ├─ External Capability Competition
   ├─ Agent Evolution
   ├─ Guarded Harness Evolution
   └─ Cross-Project Generalization
```

**겉은 단순하게, 내부는 확인 가능하게.** 평범한 작업에서는 필요하지 않은 유지보수·진화 시스템을 불러오지 않습니다.

## 실제 사용 예시

사용자:

```text
import API에 입력 검증을 추가하고 기존 오류 응답 규약은 유지해줘.
```

NULNUL은 필요하다면 다음과 같이 처리합니다.

1. 현재 프로젝트 계약과 검사를 확인합니다.
2. 관련 기억만 복원합니다.
3. 프로젝트의 API 입력 검증에 필요한 기능을 선택합니다.
4. 작업 전에 해당 기능을 준비합니다.
5. 코드를 수정합니다.
6. 저장소에서 정한 검증 명령을 실행합니다.
7. 검증된 작업 기록을 저장합니다.
8. 이후 작업과 관련이 있을 때만 해당 기록을 재사용합니다.

사용자가 요청한 것은 여전히 하나입니다. **원하는 결과를 만드는 것**입니다.

## 다른 AI 코딩 도구와 무엇이 다른가요?

NULNUL은 에이전트 팀 생성기나 거대한 프롬프트 묶음, 원격 작업 조율 서비스가 아닙니다.

| 도구 유형 | 흔한 기본값 | NULNUL 기본값 |
| --- | --- | --- |
| 에이전트 팀 생성기 | 여러 역할 생성 | 직접 실행으로도 경쟁력 있는 결과를 낼 수 있으면 이를 선택하고, 결과를 실질적으로 개선할 때만 역할 추가 |
| 프롬프트·규칙 묶음 | 준비된 지침을 불러옴 | 현재 저장소를 먼저 보고 작업에 맞는 기능만 선택 |
| 기억 관리 도구 | 대화와 컨텍스트 보존 | 대화 원문 대신 필요한 범위의 검증된 프로젝트 기억 유지 |
| 원격 작업 조율 서비스 | 원격 서비스에서 작업 흐름 실행 | 저장소 안에서 실행하며 별도 서버나 상주 프로세스 불필요 |
| 기능 마켓플레이스 | 더 많은 기능 탐색·설치 | 프로젝트에 필요한 기능이 확인됐을 때만 후보 비교 |
| NULNUL | — | 작업 완료 → 검증 → 작업 기록 → 필요할 때만 진화 |

## 근거에 따라 개선하는 Evolution

NULNUL은 “자가 개선”을 제약 없는 자기 수정으로 취급하지 않습니다.

### Capability Natural Selection

프로젝트 기능은 유지·개선·교체·병합하거나 사용을 중단할 수 있습니다. 검증된 공백이 있을 때만 새 기능을 만듭니다.

### External Capability Competition

외부 후보는 **신뢰하지 않은 상태로 격리**한 뒤 평가합니다. 존재한다는 이유만으로 일반적인 Pack 선택 대상이 되지는 않습니다.

3.1의 오프라인 준비 도우미는 검토하고 리비전을 고정한 공개 스킬 파일을 기존 로컬 디렉터리 기반 격리 경로에 맞게 준비합니다. 후보를 다운로드·설치하거나 자동으로 채택하지 않으며, “인터넷에서 최고의 스킬을 자동으로 찾는다”는 주장도 하지 않습니다.

### Agent Evolution

에이전트 구성(Agent topology)은 **누가 어떤 실행 책임을 맡는지**를 다룹니다. 직접 실행이나 단일 에이전트가 결과 면에서 경쟁력이 있으면 우선합니다. 추가하는 역할은 전문성·컨텍스트 분리·병렬 작업·독립 검증을 실질적으로 개선해야 하며, 최종 종합 책임자는 한 명으로 유지합니다.

### Guarded Harness Evolution

NULNUL은 보호되는 핵심 영역(Guarded Kernel)과 개선 가능한 제어 정책을 분리합니다. 근거가 있으면 제한된 범위에서 정책 조정이나 교체를 제안할 수 있지만, 후보가 자신의 검증 근거·승격 결과·출처·권한·롤백 규칙을 바꿀 수는 없습니다.

### Cross-Project Generalization

교차 프로젝트 재사용은 선택 사항이며, 사용자가 선택하고 승인한 기존 로컬 개인 적응 저장소(Personal Home)가 필요합니다. 프로젝트끼리 기억 원본을 복사하지 않습니다. 출처와 적용 조건을 갖추고 개인정보를 제거한 추상적 사전 지식만 후보가 될 수 있으며, 대상 프로젝트의 사실이 항상 우선합니다. 재사용하려면 호환성을 확인하고 대상 프로젝트에서도 검증해야 합니다. 공개 Meta 도입 근거는 동결된 선택기와 제한된 사례를 검증한 것이지, 보편적인 지식 전이나 모든 일반화 경로의 실사용을 증명한 것은 아닙니다.

후속 [설치 사본·실제 사용 검증](docs/live-use-validation.md)에서는 오래된 로컬 캐시를 갱신하고, 실제 영수증 버전 검사 결함을 수정한 뒤 새 Codex 세션에서 중단된 검사를 복구했습니다. 각 세션에서 완료 검사를 한 번 실행했고, 검사 12개가 모두 통과했습니다. 두 세션 모두 체크포인트를 검증하기 전에 파일 목록을 조회했습니다. 효과가 없던 문서 순서 변경도 되돌렸으므로 빠른 재개 규칙 준수나 비교 속도 개선은 주장하지 않습니다.

[세 가지 후속 업그레이드](docs/live-use-validation.md#follow-up-all-three-requested-upgrades)에서는 실행 가능한 호스트 진입 명령과 설치 파일 전체 비교를 추가했습니다. 문서 수정과 버그 수정을 위한 새 세션 두 건에서는 탐색 전에 체크포인트를 검증하고 완료 검사를 한 번 실행했으며, 중단된 검사도 복구했습니다. 로컬 전용 도입은 목록 조회 조건을 보완한 뒤 기존 코드와 역할을 보존했습니다. 전체 로컬 검사 476개가 통과했습니다. 별도 스킬을 불러오거나 도입 후 검사를 추가로 실행한 점은 한계로 남겼습니다. 이 당시 관찰만으로 비교 속도 개선이나 공개 릴리스 완료를 주장하지는 않습니다.

[지침 라우팅 평가](docs/instruction-routing.md)는 모델 호출을 8회 시도한 뒤 NO_PROMOTION(승격 없음)으로 종료했습니다. 첫 평가기는 무효 처리했고, 수정 평가기에서도 후보의 미확인 실행 기록 때문에 합격 근거가 부족했습니다. 해당 실험에서 바꾼 제품과 지침은 이전 상태로 복원했으며, 검증된 로컬 평가기 수정과 기각 근거만 남겼습니다. 아래 동결된 3.1.0 근거는 그대로 유지합니다.

## 3.1에서 추가된 기능

공개된 **3.1.0** 기준 버전은 아래 검증을 통과했습니다. 3.0 상태 형식, 빠른 재개, 기존 채택 권한과 스킬만 포함하는 제품 경계를 유지하면서 여섯 가지 작업 실행 기능을 추가했습니다.

1. [경계면 QA](plugins/nulnul-harness/skills/nulnul-harness/references/workflow-delivery.md): 실제 생산자와 소비자를 함께 확인하고, 단계별 통합 검사와 실패 조건을 재현하는 대조군을 유지합니다.
2. [업무별 절차](plugins/nulnul-harness/skills/nulnul-harness/references/workflow-recipes.md): 웹/API 변경, 데이터 마이그레이션·동기화, 근거 기반 조사를 다룹니다.
3. [실행 패턴](plugins/nulnul-harness/skills/nulnul-harness/references/workflow-delivery.md): 기존 역할과 작업 인계를 활용하는 조건부 패턴 6개를 제공합니다. 특정 팀 구성이나 모델을 강제하지 않습니다.
4. [부분 재실행](plugins/nulnul-harness/skills/nulnul-harness/scripts/workflow_delivery.py): 변경의 영향을 받는 의존 관계의 기존 검증 결과를 무효화하고 현재 계약·입출력 지문이 일치하는 검증 결과만 재사용합니다.
5. [스킬 채택 사례](plugins/nulnul-harness/skills/nulnul-harness/references/skill-acceptance.md): 실제 사용, 비슷해 보이지만 적용하지 않아야 할 요청, 후속 요청을 프로젝트 검사 근거와 함께 기록합니다.
6. [오프라인 후보 준비](plugins/nulnul-harness/skills/nulnul-harness/references/external-candidate-preparation.md): 검토한 고정 리비전의 스킬을 기존 격리·비교 절차에 맞게 준비합니다. 다운로드·설치하거나 채택을 승인하지는 않습니다.

필요한 참조만 읽습니다. 계획 영수증과 개발 점수는 보조 자료입니다. Foundation 근거나 승격 권한을 대신하지 않으며, 비공개 최종 평가 결과나 실사용 품질 향상을 입증하지도 않습니다. 새로운 상태 마이그레이션은 필요하지 않습니다.

공개 도입에서 확인한 세 가지 문제를 수정했습니다. ## 안전성과 개인정보

NULNUL은 중요한 경계를 명시적으로 유지합니다.

- **저장소 안에서 실행:** NULNUL용 서버나 상주 프로세스가 필요하지 않습니다.
- **원본 근거는 로컬에만 보관:** 대화 원문과 런타임 이벤트는 일반적인 영구 기억에 넣지 않습니다.
- **프로젝트 기억 격리:** 다른 프로젝트의 기억 원본을 복사하지 않고, 추상화한 사전 지식만 재사용합니다.
- **외부 후보 격리:** 후보를 발견했다고 권한을 부여하거나 신뢰하지 않은 설치 동작을 실행하지 않습니다.
- **기능 지침과 권한의 분리:** 스킬을 불러왔다는 이유만으로 프로젝트나 하네스의 구조를 바꿀 권한을 얻지 않습니다.
- **프로젝트가 정한 검증:** 모델이 작성한 성공 메시지가 결정론적 검사 영수증을 대신하지 않습니다.
- **트랜잭션으로 변경 관리:** 상태 변경은 검증과 출처 보존을 거치며, 실패하면 이전 상태로 되돌립니다.
- **신뢰 권한은 사용자와 호스트가 관리:** NULNUL이 임의로 신뢰 권한을 확보하지 않습니다.

전체 경계는 [SECURITY.md](SECURITY.md), [PRIVACY.md](PRIVACY.md)를 확인하세요.

## 프로젝트에 어떤 파일을 추가할 수 있나요?

NULNUL은 기존 프로젝트의 구성과 지침을 우선 재사용합니다. 세션 간 보존할 상태도 실제 용도가 있을 때만 추가합니다.

추가하거나 관리할 수 있는 파일은 다음과 같습니다.

- 활성 호스트의 관리 지침이 담긴 `AGENTS.md` 또는 `CLAUDE.md`
- 안정적인 프로젝트 사실과 검사 명령을 담은 `docs/nulnul/project.md`
- `docs/nulnul/` 아래에 필요한 범위만 저장하는 체크포인트·세션·작업 기록·기억 상태
- 기존 기능으로 작업을 처리할 수 없을 때만 추가하는 프로젝트 전용 스킬

활성 호스트의 진입점만 수정합니다. Codex는 `AGENTS.md`, Claude Code는 `CLAUDE.md`를 소유합니다. 다른 호스트를 순차적으로 도입해도 비활성 진입점은 보존하고, 같은 공유 계약과 하나의 상태 기록 주체를 재사용합니다. 두 호스트가 공유 상태를 동시에 수정하는 것은 지원하지 않습니다.

[3.0 업그레이드 안내](docs/upgrade-3.0.md)의 기반 구조 마이그레이션과 소유권 규칙은 계속 적용됩니다.

## 내부를 확인하고 싶다면

일반적인 사용 절차는 간단하게 유지하면서 내부 판단 과정을 확인할 수 있게 설계했습니다.

고급 사용자는 다음을 확인할 수 있습니다.

- 왜 이 기능이 선택됐는가?
- 어떤 프로젝트 검사가 실행됐는가?
- 어떤 검증된 작업 기록이 저장됐는가?
- 다음 세션에서 어떤 기억이 복원됐는가?
- 왜 진화 절차에서 변경 대신 `KEEP`을 선택했는가?
- 어떤 기능·에이전트·하네스 버전이 결과를 만들었는가?

보존한 기록은 출처와 이력으로 연결됩니다. 일반적인 상태 확인을 위해 대화 원문 전체를 읽을 필요는 없습니다.

## 현재 한계

NULNUL은 기록된 근거가 뒷받침하는 범위 안에서만 주장합니다.

- 스킬 `KEEP`(유지) 경로에는 실사용 근거가 있지만, 자연스럽게 발생한 스킬 `UPGRADE`(개선) 사례는 아직 공개 근거에서 관찰되지 않았습니다.
- 외부 기능 비교에는 출처 확인과 격리 절차가 구현되어 있지만, 인터넷 전체에서 최고의 기능을 찾는다고 주장하지 않습니다.
- 에이전트 진화 절차는 구현되어 있지만, 다중 에이전트가 단일 에이전트보다 항상 낫다고 주장하지 않습니다.
- 하네스 진화는 정해진 보호 경계 안에서 제어 정책을 바꾸는 범위에 한정됩니다. 무제한 재귀적 자기 진화는 지원하지 않습니다.
- 교차 프로젝트 일반화에는 개인정보 검증 절차가 있지만, 모든 프로젝트에 지식이 전이된다고 주장하지 않습니다.
- Codex와 Claude Code는 호스트에 독립적인 핵심 기록을 공유하지만, 실제 지원하는 기능의 범위는 다를 수 있습니다.

이 한계들은 숨겨진 TODO가 아니라 현재 제품의 명시적인 경계입니다.

## NULNUL + Trace: 결과를 설명할 수 있는 실행 근거

로컬 실행 검증을 통과한 연동 후보이며, 공개된 v3.1.0의 고정 릴리스 근거에 포함되지 않습니다.
NULNUL은 기존 런타임 기록에서 민감 정보를 제외하고, 스키마 버전이 명시된 근거로 정리하여
[NULNUL Trace](https://github.com/SeoNaRu/nulnul-trace)에 전달합니다.
핵심은 **기능 선택 → 실제 본문 로드 → 작업 → 프로젝트 검사 → 작업 결과**를
소스 다이제스트와 함께 연결한다는 점입니다.

Trace는 프로젝트 설정과 실제 사용을 구분하고, 영수증·파일·검증 명령의 유효성을 확인하며,
검증된 결과, 근거가 부족한 상태, 제한된 범위의 비용 지표를 표시합니다. 별도 모델 호출, 원문 대화 전송,
하네스 상태 수정, 비교 없는 개선율 주장은 하지 않습니다. 토큰 절감과 새 세션 재개 성공은
아직 측정하지 않았습니다. [근거 계약](plugins/nulnul-harness/skills/nulnul-harness/references/trace-evidence.md)을 참고하세요.

### Trace에서 하네스가 하는 일 보기

1. 업데이트된 하네스 근거 생성 코드로 새 Foundation 작업을 실행합니다. 설정만 하거나 이전 세션을 여는 것만으로 실행 근거가 생기지는 않습니다. 설치된 플러그인도 별도로 업데이트해야 합니다.
2. 버전이 맞는 Trace API·웹·수집기를 실행합니다. DB를 업데이트할 때는 기존 `pnpm db:push` 명령으로 추가 테이블을 적용합니다.
3. 세션 티켓에서 **하네스가 한 일**을 펼치고 **이번 세션** 또는 **이 프로젝트**를 선택합니다. 기능 선택·본문 로드·영수증에 연결된 결과는 구분해서 표시합니다.

### 로컬 검증 결과 (2026-09-09)

아래는 당시의 로컬 연동 검증 기록입니다. 현재 3.2.0의 공개 릴리스 근거와 구분합니다.

- Trace 테스트 **71/71 통과**(도메인 48/48, 수집기 23/23). API·웹 빌드도 통과했습니다.
- 결정론적 연동 검증에서 공식 런타임 이벤트 12개, 작업 1개, 영수증에 연결된 검사 통과 결과 1건이 수집기·API·브라우저까지 전달됐습니다. 세션·프로젝트 범위, 영수증 출처, 모바일 너비 390px 표시를 확인했습니다.
- API의 실패 조건 검증 통과: 재전송 중복 방지, 잘못된 프로젝트·세션, 민감 정보 필드 거부, 인증 누락, 다른 기기의 세션·프로젝트 접근 차단.
- 당시 Harness 작업 공간에서는 **447/448개 검사가 통과**했습니다. 남은 제품 경계 검사 실패는 기존 `docs/research` 디렉터리 때문이었으며, 통과를 만들기 위해 삭제하거나 검사에서 제외하지 않았습니다.
- 별도 공개 기준 복사본은 448개 테스트 중 실패 5개·오류 6개로 전체 통과하지 못했습니다. 고정 근거의 소스 식별 불일치 등이 포함되며, 깨끗한 릴리스 검증으로 취급하지 않습니다.
- 문서 부채 검사는 통과했습니다. 당시 Release Gate는 변경된 근거 생성 코드에 맞는 공개 Claude·교차 프로젝트 Meta 도입 근거가 없어 `release_ready: false`였습니다.
- 합성 데이터와 임시 DB 스키마로 진행한 검증이며 실제 사용자·모델 실험이 아닙니다. 임시 서버·스키마는 제거했고 기존 세션은 건드리지 않았습니다. 추가 모델 호출 **0회**. 전역 플러그인 갱신·푸시·릴리스는 하지 않았습니다.

### 요청 중심 연동 갱신 (2026-09-09)

Trace 첫 화면을 사용자 요청별 결과·검증·다음 행동으로 바꿨습니다. **하네스가 한 일**은 연결됨·기록 없음·이전 형식·세션 미연결을 구분하며, `nulnul-trace doctor`로 로컬 원인을 확인합니다. 당시 명시적으로 요청한 연동 작업을 위해 로컬 Codex 설치 플러그인도 갱신했습니다.

당시 코딩 세션의 실제 작업에서 `trace-core-purity`를 선택하고 본문을 로드한 뒤 Foundation 검사 통과 영수증이 실행 중인 수집기·API·브라우저에 도착했습니다. 앞서 시작 과정에서 중단된 실행 기록은 부분적으로만 관측된 결과로 남겼습니다. 실제 개발 실행 한 건이며 통제된 모델 비교나 절감 효과의 근거는 아닙니다.

소스 상태를 확인할 때는 Git 추적 파일과 무시되지 않은 미추적 파일을 기준으로 삼으며, 무시 규칙에 걸려도 추적 중인 파일은 포함합니다. 의존성·빌드 폴더 때문에 시작 단계가 전체 작업 트리를 훑던 문제를 해결했습니다. 로컬 Trace에서 다이제스트 계산만 약 2.1초였으며 전체 실행 성능 측정은 아닙니다. 회귀 검사 2개를 추가했습니다. 당시 다시 패키징한 뒤 Harness 전체 검사 **449/450개가 통과**했고, 기존 `docs/research` 제품 경계 검사 실패만 남았습니다. 공개 릴리스의 고정 근거는 변경하지 않았습니다.

## 3.2의 작동 상태 확인

Trace를 열지 않고도 NULNUL이 무엇을 하는지 확인할 수 있습니다. 읽기 전용 상태 명령은
개발 소스·명시적으로 검사한 설치 사본·호스트 세션 연결·작업 상태·기능 선택과 그 이유·
변경 내용·검증 근거를 구분합니다.

~~~bash
python3 plugins/nulnul-harness/skills/nulnul-harness/scripts/harness_status.py --root . --lang ko
~~~

호스트가 실제 세션 키를 제공합니다. 연결 여부를 확인하지 못했다는 것이 작동하지 않는다는 뜻은 아니며, 과거 기록 조회는
현재 실행의 증거가 아닙니다. 플러그인이 설치·활성화되어 있어도 이미 열린 스레드가 최신
스킬 본문을 읽었다고 단정하지 않습니다. 검사 종료 기록과 검증된 과거 영수증도 구분합니다.
알림·추가 모델 호출·전역 설치·두 번째 상태 기록 주체를 추가하지 않습니다.

기존 연구 자료는 삭제하지 않고 제품 밖에 보존합니다. 패키징은 배포 플러그인 안의 과거
실험실 경로와 심볼릭 링크를 거부하며, 아카이브 타임스탬프·권한 정규화는 유지합니다.

로컬 근거 검사와 공개 가능 여부 판정은 다른 명령입니다.

~~~bash
python3 scripts/release_gate.py
python3 scripts/public_release_gate.py
~~~

두 번째 명령은 `release_ready`가 정확히 true가 아니면 실패합니다. main 브랜치와 main을 대상으로 한 PR에는
엄격한 판정을, 그 밖의 후보 브랜치에는 로컬 근거 검사를 적용합니다. 변경된 후보를 인증된 것처럼
보이게 하려고 고정된 판정기나 과거 채택 근거의 해시를 덮어쓰지 않습니다.

업데이트한 3.2.0은 전체 저장소 검사 481개를 통과했습니다. 실제 Trace 프로젝트에서는 따옴표로 감싼 검증 경로 인식을 수정했고, 검토한 두 파일을 반영한 원본 작업 폴더의 완료 검사도 통과했습니다. 새 세션에서 설정 설명을 두 번 변경했을 때 모두 기존 영수증을 재사용해 완료 검사를 추가 실행하지 않았고, 최초 중복 실행 실패 기록도 보존했습니다. 공개 3.2.0 버전으로 수행한 Claude·Meta 도입 검증도 통과했으며, 릴리스 근거는 이 로컬 관찰과 구분합니다. 비교 우위를 주장하지 않습니다.
